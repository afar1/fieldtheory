# Voice delivery backend tests

Run `npm ci && npm test` here. The suite loads the delivery and timeline migrations into PGlite (PostgreSQL in WASM), with local auth and Realtime fixtures. It tests SQL execution, lease fencing, owner isolation, idempotence, and explicit start evidence. It does not contact Supabase or verify hosted WebSocket delivery.

## Timeline migration review

`20260910001000_voice_delivery_timeline.sql` is additive and must be reviewed before hosted application. It does not enable delivery, execute backlog, change existing dispatch RPCs, or backfill historical events from ambiguous timestamps.

- `voice_delivery_events`: owner-readable events keyed by job and stage, with transcript ID and text revision. Upload, first claim, and terminal outcomes come from authoritative job changes. `dispatch_started_at` remains authorization to try dispatch; it never produces a `started` event.
- `voice_jobs_record_progress`: accepts `queued` and `started` against a current owner/generation/lease and the recorded thread. Actual start requires a turn ID. `time_source` distinguishes server timestamps, Codex-reported start times, and locally observed fallback times. Replays of an already recorded identical stage/thread/turn are safe after the lease ends. Conflicting or unrecorded stale-lease observations return `ok: false`.
- Completion can recover `queuedAt` and `startedAt` observations from the result if progress reporting failed. Only explicit ISO timestamps within the recording's plausible time window are used, and start also requires `turn_id`. Malformed optional observations do not discard the final result.
- `voice_runner_report`: owner-authenticated structured Mac observations. `p_expected_owner` fences a token/account change between capture and transport. Nullable booleans represent unknown state. History retains event time and server receipt time; delayed observations cannot overwrite newer presence state. Runner history is pruned after 30 days on the owner's next report. The latest presence remains and its timestamp must be interpreted as freshness, never continuous proof of availability.
- All client table writes are denied. New RPCs grant execution only to authenticated users. Timeline notifications use the existing private owner topic `voice-jobs:<user-id>`, event `voice_delivery_changed`, with no transcript, output, folder, or error details. Notification failure does not roll back observability records or execution.

A deployment smoke test must check owner-only private channel delivery and a real phone/Mac flow, including lock/sleep correlation. Until deployment, clients must tolerate missing tables/RPCs. A local passing test is not evidence that the hosted migration or phone update is active.

## Parallel submission migration

`20260913120000_voice_parallel_submission.sql` adds a destination submission gate under the existing authenticated owner transaction lock. `voice_jobs_record_dispatch` assigns an immutable `submission_order`; `voice_jobs_begin_dispatch` returns `{ok:false, blocked:true, job}` until earlier registered jobs for that destination have acknowledged submission. Clients must retain/renew their job lease while waiting and never submit before authorization succeeds.

`voice_jobs_accept_submission(job_id, lease_token)` must follow exact acknowledgement or recovery evidence of a submission whose live owner guarantees queue draining. This client uses early release only for externally owned `thread/queue/add`; direct executions keep the gate until completion. It records `submission_accepted_at` without claiming the queued task has started, and releases the gate while execution continues under its observation lease. Stale leases, wrong owners, and non-running jobs cannot acknowledge. Retry is idempotent within the live lease. Missing acknowledgment conservatively blocks the destination until recovery or a resolved terminal outcome; `needs_user` with `recovery_uncertain` also holds it. Existing clients need not call a new RPC: they hold their destination gate until completion, preserving safety at lower concurrency.

Ordering is destination-registration order, not recording creation order: a recording whose destination is still unknown cannot yet participate. The gate does not synchronize a shared local routing catalog or shared desktop resources, and does not provide exactly-once delivery for Codex's non-deduplicating queue RPC. Existing ambiguity/recovery handling remains essential. Transcript revisions retain their existing stronger completion-order fence.

The suite exercises 15-recording bounded claims, cross-worker gate release, unrelated destinations, legacy conservatism, immutable registration, uncertainty, owner checks, expired leases, and recovery. PGlite checks SQL behavior with simulated identities; it does not establish real concurrent hosted transaction behavior or device/runtime success.

`voice_jobs_submission_ready(job_id, lease_token)` runs the same gate predicate without changing dispatch state. The manager uses it before `thread/resume` so a direct-run owner on another Mac can finish and release ownership before runner mode selection. It returns the same blocked/invalid shapes as `begin_dispatch`; callers must still execute `begin_dispatch` immediately before actual submission. Direct-run execution retains the gate through completion unless its runtime owns queue draining; only durable externally managed queued acceptance releases early.
