# The Two Hard Problems

Phil Karlton famously quipped that there are only two hard things in computer science: cache invalidation and naming things. Our Librarian bug exemplifies the first with painful clarity. The system maintains an in-memory cache of readings, loaded from a persisted index at startup. When a new reading file appears on disk, the watcher checks `!cache.has(path)` to determine if it's "new"—but if the index was written after the file was created, the cache already contains the entry, and the reset logic never fires.

This mirrors a classic distributed systems problem: the cache and the source of truth (the filesystem) have drifted out of sync, and our invalidation strategy trusted the cache when it shouldn't have. The fix requires treating filesystem mtime as authoritative—comparing the file's modification timestamp against what we've recorded, not merely checking for key presence. Leslie Lamport's work on logical clocks in the 1970s established that in distributed systems, you cannot rely on simple existence checks; you need timestamps or version vectors to establish ordering. Our Librarian, in its small way, is a distributed system: Claude Code writes files, Electron watches them, and the status file tracks state. Without proper temporal ordering, the cache lies.
