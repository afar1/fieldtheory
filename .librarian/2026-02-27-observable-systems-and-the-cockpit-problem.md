# Observable Systems and the Cockpit Problem

The Boeing 737 MAX crashes taught aerospace engineering a lesson that software systems rediscover constantly: hidden state kills. In both Lion Air 610 and Ethiopian Airlines 302, the MCAS (Maneuvering Characteristics Augmentation System) operated in a condition the pilots couldn't observe — a single angle-of-attack sensor feeding bad data into an authority loop that overrode human input. The system had a state (`engaged`) but no condition (`degraded-single-sensor`). The cockpit instruments showed the aircraft was fine until it wasn't.

When you build a system that has an `idle | listening | recording` state enum, you've built the cockpit instruments. They tell the operator what mode the system is in. But they don't tell the operator whether the system is *healthy* in that mode. A microphone can be in `listening` state while its transcription engine is cold, its chunk queue is backing up, or its primary model has silently failed over to a slower fallback. The state is correct. The condition is degraded. And without a separate axis for condition, the operator has no way to distinguish "everything is fine" from "we're three failures away from dropping audio."

This is the cockpit problem: the instruments report what you asked them to report, not what you need to know. Fixing it requires what control theory calls **observability** — the mathematical property that all internal states of a system can be inferred from its outputs. In a linear system, observability is binary: you either have enough sensors, or you don't. In software, observability is a spectrum. Logs are the weakest form (information exists but is unsearchable at runtime). Metrics are stronger (aggregated, queryable). But the strongest form is *structured condition*, where the system itself computes a summary of its health and exposes it through the same channels as its operational state.

The key insight is that state and condition are orthogonal axes. State describes *what the system is doing*. Condition describes *how well it's doing it*. A hot mic can be `listening + ready`, or `listening + degraded`, or `listening + warming`. These aren't sub-states — they're a separate dimension of truth that the original enum collapsed into a single bit of information.

Backpressure is the dual of observability. Where observability asks "can I see what's happening?", backpressure asks "does the system protect itself when things go wrong?" An unbounded queue is the software equivalent of a fuel tank without an overflow valve. It works perfectly right up until it doesn't, and when it fails, it fails catastrophically — memory exhaustion, cascading latency, stale data delivered as if it were fresh. A bounded queue with explicit drop semantics is not elegant. But it is honest about the system's capacity, and honesty is the foundation of reliability.

The engineers who designed TCP understood this. The sliding window protocol doesn't just manage throughput — it makes congestion *visible*. When packets are dropped, the sender knows. It backs off. The system degrades gracefully instead of collapsing. Every reliable distributed system, from TCP to Kafka to the human nervous system's pain reflex, shares this property: degradation is a first-class signal, not an accident.
