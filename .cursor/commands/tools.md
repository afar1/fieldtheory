# tools

We build the system so the model does the hard part it is good at, understanding messy human language, making reasonable inferences, and choosing the right next action, while the product supplies a small set of clear, trustworthy tools and a thin deterministic layer around them. We do not try to encode the whole product in prompts, and we do not build heavy orchestration for every edge case. Instead, we make state explicit, keep tool contracts clean, preserve canonical truth in structured systems, and let the model operate over a bounded working set rather than an ever-growing transcript. We are deliberate about token economy: do not keep stuffing more history, prompts, or rules into context when a small piece of structured state, a lookup, an index, or a targeted tool call will do. When something must be exact, like identity, permissions, state transitions, timestamps, or whether an action really happened, the system handles it deterministically. When something is interpretive, like what a user means by “it,” “same time,” or “can you handle this,” we lean on the model first, then support it with lightweight retrieval, resolvers, and partial-update semantics. The goal is always the same: thin layers, strong tools, bounded context, observable behavior, minimal prompt bloat, and a product that feels intelligent because the model is well-supported, not because we buried it under rules.
