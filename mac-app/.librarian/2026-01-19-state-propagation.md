# State Propagation and the Observer Problem

In 1994, the Gang of Four documented the Observer pattern in their seminal "Design Patterns" book, but the real insight came from earlier work on Model-View-Controller at Xerox PARC. The problem they identified wasn't about updating state—it was about *notifying dependents* when state changes. A model can change perfectly, but if the view doesn't know to re-render, the user sees stale reality. This is exactly what's happening with the tray menu: Main resets `onboardingComplete` to false, but TrayManager—an observer that should care about this state—was never told to look again.

The fix is almost trivially simple: after changing the state, tell the dependent to update. But the bug reveals a design smell. TrayManager subscribes to `quotaChanged`, `tierChanged`, and `stateChanged`, yet not to preference changes. The pattern was established but not completed. This is the kind of inconsistency that creeps in when features are added incrementally—each addition solves its immediate problem without auditing whether the same pattern applies elsewhere. The two-line fix works, but the deeper lesson is that subscription patterns should be systematic, not ad-hoc.
